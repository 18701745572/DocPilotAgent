# ADR-005: 文档先行，代码后置

- **状态**：Accepted
- **日期**：2026-08-24
- **决策者**：用户 + 项目设计
- **关联**：[README.md](../../README.md)、[ROADMAP.md](../ROADMAP.md)、[TRACEABILITY.md](../TRACEABILITY.md)

## 背景

用户要求"以终为始"：先完成最终形态的全部文档，再启动开发。传统做法是边写代码边补文档，导致：
- 文档滞后于代码，常失真
- 决策散落在 commit message / 脑海里，难追溯
- 验收无基准（"做完了"没有客观标准）

## 决策

采用**文档先行**策略：在写任何代码前，先产出最终形态的完整文档集（规格/设计/接口/验证/管理/运营），代码后续按 [ROADMAP.md](../ROADMAP.md) 阶段实现，每阶段对照文档验收。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 代码先行，文档后补 | 快速看到可运行物 | 文档易失真；决策难追溯 |
| B. 文档与代码并行 | 平衡 | 协调成本高；易脱节 |
| C. 文档先行（**采纳**） | 决策可追溯；验收有基准；利于"可仿写"定位 | 启动慢；前期无可见产物 |
| D. 仅写 README | 最轻 | 无法支撑复杂智能体的约束与评估 |

## 理由

- 项目定位"可仿写"，文档本身是产物之一
- 智能体约束（权限/记忆/工具）复杂，需提前锁定避免实现期偏移
- [EVAL.md](../EVAL.md) 与 [TEST_PLAN.md](../TEST_PLAN.md) 需要文档作为验收基准
- 用户明确要求

## 影响

- 文档集版本独立管理（`docs-vN`，见 [CHANGELOG.md](../CHANGELOG.md) §1）
- [ROADMAP.md](../ROADMAP.md) P0~P7 每阶段对应文档验收
- [TRACEABILITY.md](../TRACEABILITY.md) 维护文档 ↔ 代码 ↔ 测试 ↔ 评测的追溯
- 代码实现必须满足文档；文档变更触发代码回归（见 [CHANGELOG.md](../CHANGELOG.md) §4）

## 后续追踪

- 落地位置：整个 `docs/` 目录
- 验证方式：[RELEASE.md](../RELEASE.md) §3 文档门禁
- 复盘触发：若发现文档与实现严重脱节，评估是否回退到 B 方案
